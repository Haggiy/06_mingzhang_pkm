# 导入智能分类 ML 设计

> 状态：设计文档（已确认）
> 来源：2026-05-12 头脑风暴，用户确认所有设计决策
> 范围：导入时用机器学习从已标注记录学习，自动推断新导入记录的收付类型和类型明细

> 执行裁剪（2026-05-14）：v1.0 / MVP 不执行完整 ML 分类。当前只实现保守记忆预填：同来源、同商户、同商品且历史确认分类完全一致时，预填 `收付类型` 和 `类型明细`；冲突或无历史时留空。逻辑回归、实时训练、置信度阈值和 LLM 链路保留为后续实验方案，不作为 MVP 验收条件。

## 1. 目标

在支付宝/微信账单导入流程中，利用用户历史已标注数据训练轻量分类模型，自动预填新导入记录的 `收付类型` 和 `类型明细`，减少手动分类操作。

## 2. 设计决策汇总

| 决策项 | 原设计 | 实验修正 |
|--------|------|---------|
| 算法 | 多分类逻辑回归 + 特征哈希 | 同左，外加商户 onehot 编码（C=0.5 正则化，实验验证最优） |
| 预测目标 | 收付类型 + 类型明细（两级分层预测） | 同左，实验验证 L1 本地 77.5%、L2 本地 66.5% |
| 输入特征 | 交易对方、商品说明、交易类型、金额 | 三路独立 ngram（交易对方 2000维 + 商品说明 2000维 + 平台分类 500维）+ 金额分桶 + 商户 onehot |
| 训练策略 | 每次导入时拉取最新已标注数据，实时 SGD | 同左，全量训练（数据量小时）+ 超 5000 条随机采样 |
| 推理呈现 | 置信度 < 0.6 留空 | 同左。实验表明 0.6 阈值下高置信准确率 83%，0.7 阈值下 84.4%，均可接受 |
| 冷启动 | < 30 条已标注不预测 | 同左。此外首层记忆引擎不受冷启动影响（1 条即可工作） |
| 模型持久化 | 不做缓存 | 同左。但记忆引擎字典应持久化（纯 KV 映射，非模型权重） |
| 架构 | 两层：ML → 用户 | **修正为三层：记忆引擎 → ML → 用户**（见 3.1 节） |
| 平台 | 纯 Swift + Accelerate | 同左，记忆引擎用 Dictionary 即可 |

## 3. 整体架构

### 3.1 三层分流架构（实验修正）

实验验证（见第 10 节）表明，纯两层（ML → LLM）方案中新商户学习太慢（需 3-5 次标注才能到高置信度），而简单记忆规则在商户复用场景下准确率 85-90%。因此修正为**三层分流**：

```
支付宝/微信 CSV → 解析 → 候选记录列表
                            ↓
         ┌─ 第1层: 记忆引擎 ──────────────────┐
         │  同商户+同商品 → 复用上次标签 (89.9%)  │
         │  同商户历史一致 → 复用上次标签 (87.7%)  │
         │  命中 → 直接预填，零训练开销            │
         └────────────────────────────────────┘
                            ↓ 未命中
         ┌─ 第2层: 本地ML模型 ─────────────────┐
         │  Level 1: 收付类型 (逻辑回归 + 特征哈希) │
         │  Level 2: 类型明细 (按L1分组独立模型)    │
         │  置信度 ≥ 0.6 → 预填                   │
         │  置信度 < 0.6 → 留空给用户              │
         └────────────────────────────────────┘
                            ↓
              导入预览页面（预填字段有视觉标记）
                            ↓
              用户确认/修改 → 记录入库 → 记忆表+训练集更新
```

### 3.2 分流比例预估

基于 16,021 条真实数据实验：

| 层级 | 覆盖比例 | 准确率 | 延迟 |
|------|---------|--------|------|
| 记忆引擎 | ~50-60% | 87-90% | 微秒级（字典查表） |
| 本地 ML | ~25-35% | 83-85% | 毫秒级 |
| 用户手动 | ~10-15% | — | — |

### 3.3 原两层架构（已废弃）

```
支付宝/微信 CSV → 解析 → 候选记录列表
                            ↓
              已标注记录（从数据库拉取最新）
                            ↓
              实时训练 → Level 1 模型（收付类型）
                       → Level 2 模型（类型明细，按收付类型分组）
                            ↓
              逐条推理 → 置信度 >= 0.6 预填
                       → 置信度 < 0.6 留空
                            ↓
              导入预览页面（预填字段有视觉标记）
                            ↓
              用户确认/修改 → 记录入库
```

两级分层预测保证 `类型明细` 永远归属正确的 `收付类型`，符合 Spec 约束。

## 4. 特征工程

### 4.1 文本特征（交易对方、商品说明、交易类型）

三个文本字段分别提取字符级 n-gram（2-gram、3-gram、4-gram），通过特征哈希映射到固定维度向量：

```text
"京东商城" → 补边界: "<京东商城>" 
→ 2-gram: "<京", "京东", "东商", "商城", "城>"
→ 3-gram: "<京东", "京东商", "东商城", "商城>"
→ 4-gram: "<京东商", "京东商城", "东商城>"
```

每个 n-gram 哈希到固定维度索引：

```swift
func hashFeature(_ ngram: String, dim: Int) -> Int {
    abs(ngram.hashValue) % dim
}
```

不处理哈希冲突（特征哈希标准做法）。

### 4.2 数值特征（金额）

- 金额取绝对值后 log 分桶：`0~1, 1~10, 10~50, 50~200, 200~1000, 1000~5000, 5000+`（7 桶）
- 收/支/中性方向标记（3 个二值特征）
- 桶编码同样做特征哈希，写入同一向量

### 4.3 商户身份特征（实验验证关键特征）

实验证明商户 onehot 是提升准确率最有效的单一特征：

```python
# 每个商户独立维度，未见过商户置零
merch_enc = OneHotEncoder(sparse_output=True, handle_unknown="ignore")
X_merchant = merch_enc.fit_transform([[r["交易对方"]] for r in train_rows])
```

实验消融结果：加入商户 onehot 后本地 L1 准确率从 ~65% 提升至 ~78%。

### 4.4 特征维度

| 模型 | 维度 | 组成 |
|------|------|------|
| Level 1（收付类型） | ~4500 | ngram(交易对方2000 + 商品说明2000 + 平台分类500) + 金额分桶(16) + 商户onehot(动态) |
| Level 2（类型明细） | ~4500 | 同 Level 1 特征，更强正则化(C=0.3) |

## 5. 算法

### 5.1 模型：多分类逻辑回归（Softmax 回归）

```
z = W · x + b          (W: [k × d], x: 稀疏特征向量, b: [k])
p = softmax(z)          p[i] = exp(z[i]) / Σexp(z[j])
预测类别 = argmax(p)
置信度 = max(p)
```

推理复杂度：O(nonzero_features × num_classes)，约 80 × 11 = 880 次乘法，微秒级。

### 5.2 批量 SGD 训练

每次导入时，用当前所有已标注记录做全量批量 SGD：

```
for epoch in 1...epochs:
    for (x, y_true) in labeledRecords:
        p = softmax(W · x + b)
        for each class i: grad[i] = p[i] - (i == y_true ? 1 : 0)
        for each nonzero feature j in x:
            W[i][j] -= lr × grad[i] × x[j]
        b[i] -= lr × grad[i]
        W[i] *= (1 - lr × decay)    // L2 正则
```

学习率：`η = η0 / (1 + decay × sampleCount)`，初始 0.5，衰减 0.001。

### 5.3 训练性能

假设 2000 条已标注记录，3 epoch：
- 2000 × 50 × 11 × 3 = 3,300,000 次乘法
- 用 Accelerate BLAS 预计 20-50ms

若数据 > 5000 条，随机采样 5000 条训练以保证速度。

## 7. 导入流程集成

```
1. 用户点击导入，选择支付宝/微信 CSV 文件
2. 系统解析 CSV，生成候选记录列表
3. [新] 加载记忆引擎字典（商户→标签映射，从数据库读取）
4. [新] 先走记忆引擎：同商户+同商品命中 → 直接预填
5. [新] 记忆未命中：TrainingDataProvider 拉取所有已标注记录
6. [新] 已标注数据 >= 30 条时，实时训练 ML 模型
7. [新] ML 逐条推理，置信度 >= 0.6 自动填入
8. 展示导入预览页面，预填字段有视觉标记：
   - 记忆引擎预填：绿色标记（高可靠）
   - ML 预填：浅蓝标记（建议核实）
9. 用户逐条或批量修改，补充收付手段、备注、账月
10. 用户确认导入
11. 记录入库，同时更新记忆引擎字典 + 训练数据
```

## 8. 边缘情况

| 场景 | 处理 |
|------|------|
| 训练数据 < 30 条 | 跳过 ML 预测，记忆引擎不受影响 |
| 记忆引擎与 ML 预测冲突 | 记忆引擎优先（准确率更高） |
| 某收付类型下无类型明细数据 | Level 2 对该类型不预测 |
| 用户新增收付类型 | 自动扩展 Level 1 输出维度 |
| 用户新增类型明细 | 自动扩展对应 Level 2 模型输出维度 |
| 单条置信度 < 0.6 | 留空，不做猜测 |
| 训练数据 > 5000 条 | 随机采样 5000 条训练 |
| CSV 字段缺失/乱码 | 对应特征置零，仍可基于其他特征预测；记忆引擎不受影响 |
| 新分类无历史数据 | 权重随机初始化，随 SGD 逐步学习 |
| 用户修改记忆引擎预填 | 更新记忆字典（以用户最新标注为准） |
| 同商户不同商品属于不同类别 | 粒度自动降级：同商户+同商品 → 仅同商户 → ML |

## 9. 不做

- 不做模型缓存/持久化（每次实时训练）。**但记忆引擎的商户→标签映射应持久化到数据库**
- 不做预训练基础模型
- 不做收付手段、备注、账月的 ML 预测
- 不接入外部 AI API（纯本地方案）
- 不使用 Core ML 导出管线

### 10.1 实验历程

| 版本 | 日期 | 内容 | 关键发现 |
|------|------|------|---------|

### 10.2 最优模型配置

```python
# 特征
三路独立 ngram:
  交易对方: char_wb (2,4) ngram, max_features=2000, sublinear_tf=True
  商品说明: char_wb (2,4) ngram, max_features=2000, sublinear_tf=True
  平台分类: char_wb (2,3) ngram, max_features=500,  sublinear_tf=True

商户 onehot: 所有出现过商户, handle_unknown="ignore"
金额分桶: [0,1,3,5,8,10,15,20,30,50,100,200,500,∞] + 收/支方向(3维)

# 模型
L1: LogisticRegression(multi_class="multinomial", C=0.5, class_weight="balanced")
L2: 每个 L1 独立 LogisticRegression(C=0.3, class_weight="balanced")
    样本<10 → 回退到多数类
    只有1个明细 → 直接返回

# 训练
冷启动: 30 条已匹配种子
每次导入: 全量已标注数据重训
仅标准分类记录进入训练集
```

### 10.5 主要混淆对

```
文娱游购 → 生活必要    290次   （伙食费 vs 饮食游乐费，ngram 无法区分）
生活必要 → 文娱游购    171次   （互逆混淆）
其他必要 → 生活必要     92次
投资自身 → 生活必要     26次
```

根本原因：n-gram 特征对语义边界的区分能力有硬天花板。"伙食费" vs "饮食游乐费"、日常购物 vs 其他必要家用 —— 这些边界需要理解消费场景，纯字符特征无法捕捉。

### 10.6 置信度与阈值

| 阈值 | 高置信占比 | 高置信L1准确 | LLM调用率 |
|------|-----------|-------------|-----------|
| 0.80 | 63.7% | 85.4% | 36.3% |
| 0.75 | 68.3% | 85.1% | 31.7% |
| 0.70 | 72.6% | 84.4% | 27.4% |
| **0.60** | **81.3%** | **83.0%** | **18.7%** |

纯本地方案建议阈值 **0.6**（高占比 81% 且准确率 83% 可接受）。

### 10.7 新商户学习速度

分析 317 个首次出现为低置信的商户：

| 标注次数 | 下次即高置信 | 累计达高置信 |
|---------|------------|------------|
| 1 次 | 11.4% | 11.4% |
| 2 次 | 9.8% | 21.2% |
| 3 次 | 3.8% | 25.0% |
| 5 次 | — | 28.3% |

逻辑回归学新商户很慢：onehot 特征在数千维中被 C=0.5 正则化压制，需 3-5 个同标签样本才能建立统计显著性。**55% 的低频商户在观察期内永远达不到高置信**。这是引入记忆引擎的根本原因。

### 10.8 记忆规则 vs ML 模型

| 策略 | 准确率 | 学习速度 | 实现 |
|------|--------|---------|------|
| 同商户+同商品 → 复用 | **89.9%** | 1 次标注 | Dictionary |
| 同商户 → 复用 | **85.3%** | 1 次标注 | Dictionary |
| 同商户连续2次一致 → 复用 | **87.7%** | 2 次标注 | Dictionary |
| ML 模型（含商户 onehot） | 85.4% | 3-5+ 次标注 | 逻辑回归 |

记忆规则在所有维度上均优于或等于 ML 模型处理重复商户。ML 模型的价值在泛化到新商户。

### 10.9 渐进学习趋势

按季度聚合（16,021 条）：

| 季度 | 本地L1 | 高占比 | LLM率 |
|------|--------|--------|-------|
| 2023-Q1 | 64.8% | 51.7% | 48.3% |
| 2024-Q1 | 79.8% | 72.2% | 27.8% |
| 2025-Q1 | 75.9% | 81.5% | 18.5% |

三个同步趋势持续发生：高置信占比 ↑、LLM 调用率 ↓、本地准确率稳定在 75-85%。

### 10.11 关键设计启示

1. **记忆引擎必须做**。新商户学习速度的瓶颈不是调参能解决的，需要架构层面补充。
2. **ML 角色是泛化，不是记忆**。它处理"像某个类别的未知商户"，记忆处理"就是那个已知商户"。
3. **低频商户永远学不会，但不需要学会**。出现 3 次以内的大多数商户，记忆足够应对。
4. **高频商户自然学会**。频繁消费自动积累标注，模型无需特殊处理。
5. **v1.0 纯本地三层可行**。记忆+ML+用户，预估 85%+ 预填率，83-90% 预填准确率。
6. **如果未来接入 LLM**，记忆→ML→LLM 可将 LLM 率压至 10% 以下。
