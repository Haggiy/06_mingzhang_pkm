# Implementation Plan 审核提示词

> 状态：通用审核模板
> 用途：对所有 Implementation Plan 进行结构化审核，确保计划在进入执行前满足项目全局约束和 iOS 开发最佳实践。
> 使用方法：将待审核计划全文粘贴到提示词末尾，要求 AI 逐项审核并输出审核报告。

---

## 审核指令

你是一位资深的 iOS 技术负责人，正在审核一份 Implementation Plan。请按以下 10 个维度逐项审核，每个维度给出「通过 / 需改进 / 不适用」评级，并对「需改进」项给出具体修改建议。

审核原则：
- 站在项目全局利益角度，不妥协，不放过模糊地带。
- 每一条改进建议必须指向计划中的具体内容，不允许泛泛而谈。
- 如果计划中某处与项目已有权威文档冲突，必须明确指出冲突来源。

---

### 1. 证据追溯与权威来源

检查计划中的每个关键决策是否能追溯到以下权威来源（按优先级排列）：

1. `evidence/raw/` 中的 Excel/CSV/XLSX 样例
2. 用户口述确认
3. `docs/prd/mvp-prd.md`
4. `docs/specs/` 下的权威 Spec
5. `docs/work-plans/` 下的工作安排和路线图

审核要点：
- 计划开头是否明确列出依据的权威文档？
- 新增的数据结构、规则、UI 行为是否在 Spec 或 PRD 中有对应物？
- 如果某个行为在现有 Spec 中没有定义，计划是否标注为 `推断` 或 `待确认`？
- 是否有从「旧 01_mingzhang」或已废弃文档中继承的未验证假设？

---

### 2. MVP 范围边界

对照 `docs/prd/mvp-prd.md` 第 5 节「MVP 明确不做」和路线图中的范围约束。

审核要点：
- 计划是否引入了 MVP 明确排除的能力？（预算、预测、AI、云同步、结账状态、导入字段映射配置、账月规则配置、继承全局偏好配置、自动分类规则中心等）
- 计划开头是否有明确的「明确不做」小节？
- 是否存在范围蔓延（scope creep）——做的事情超出了本阶段目标所需？
- 如果计划涉及 UI，是否在设置页、流水页等位置保留了不应出现的入口？

---

### 3. 架构一致性

对照项目已确立的架构分层：

```text
SwiftUI (View/Store) → Use Case (LedgerUseCases) → Repository/DB (LedgerDatabase)
```

审核要点：
- 所有写操作是否通过 Use Case，而非 View 直接操作数据库？
- View 是否只通过 `LedgerStore` 获取数据和发起操作？
- 前端是否直接实现了账务计算规则？（这是红线）
- 新增的公开类型（struct/enum）是否放在 `MingZhangCore` 而非 App target？
- 是否明确了哪些代码放在 Core、哪些放在 App target？

---

### 4. iOS 开发最佳实践

审核要点：
- **Swift 6 并发**：所有跨边界的类型是否标记 `Sendable`？数据库操作是否在正确的 actor/dispatch 上下文中？
- **SwiftUI**：View 是否使用 `@EnvironmentObject` / `@State` / `@Binding` 正确管理状态？是否避免了在 View 的 body 中执行副作用？
- **GRDB**：数据库迁移是否正确使用 `registerMigration`？是否避免了在迁移中执行耗时操作？JSON 字段的编解码是否有明确的错误处理？
- **错误处理**：Use Case 的 throws 是否在 Store 层被正确捕获并转为用户可读的错误信息？
- **命名**：Swift API 命名是否遵循 Swift API Design Guidelines？

---

### 5. 数据完整性与迁移安全

审核要点：
- 数据库 schema 变更是否通过 migration 而非重建？
- 新增列是否有合理的默认值？
- 迁移是否兼容已有数据？（例如，新增 NOT NULL 列时必须提供 default）
- 是否有历史数据保护策略？（配置改名/停用不应改写历史流水展示）
- Snapshot 策略是否合理？哪些字段需要快照、哪些不需要？
- 停用/删除操作是否有引用完整性检查？（被流水引用的配置能否安全停用？）

---

### 6. 测试策略

审核要点：
- 每个 Task 是否采用 TDD 步骤（先写失败测试 → 实现 → 测试通过）？
- 测试是否覆盖了关键边界：空值、重复、并发、停用后的行为、引用保护？
- 测试是否可以直接在 CI 中运行（`swift test`）而不依赖模拟器？
- 是否有端到端的手动验收清单？
- 是否有回归测试步骤（确保新功能不破坏已有 P0 测试）？

---

### 7. 任务可执行性

审核要点：
- 每个 Task 是否明确列出了修改/新建的文件？
- 每个 Task 是否有清晰的、可验证的完成标准？
- Task 之间的依赖关系是否合理？是否有循环依赖？
- 每个 Task 是否可以在一次会话中完成？（粒度是否合适）
- Commit 消息是否遵循项目规范（`feat:` / `fix:` / `docs:`）？
- 是否有构建验证步骤（`xcodebuild` 或 `swift test`）？

---

### 8. 风险识别与边界条件

审核要点：
- 计划末尾是否有明确的风险点小节？
- 是否覆盖了以下典型风险：
  - 同名配置的惟一性约束
  - 并发写入冲突
  - 大规模数据下的性能
  - 迁移失败的回滚策略
  - 用户误操作（如误停用）的后果
- 对于跨 Task 的隐式依赖是否明确标注？

---

### 9. 命名与语义一致性

审核要点：
- 新增的术语和类型名是否与 Spec 中的领域术语一致？（例如：`收付手段` → `PaymentMethod`，`收付类型` → `PaymentType`，`类型明细` → `PaymentDetail`）
- 是否有与已有 Spec 中同名词但不同语义的情况？
- UI 标签和内部模型字段名是否保持对应关系？
- 枚举值的命名是否自解释？（`pendingRealAccount` vs `待补真实账户`）

---

### 10. 安全与破坏性操作

审核要点：
- 是否有可能导致用户数据丢失的操作？（删除、清空、覆盖）
- 高风险操作（如停用、恢复备份）是否有二次确认？
- 是否存在 SQL 注入风险？（所有 SQL 是否使用参数化查询？）
- 是否避免在 App 启动时执行不可逆的数据操作？

---

```markdown
## 逐项审核

### 1. 证据追溯 - [通过/需改进/不适用]
[具体发现和改进建议]

### 2. MVP 范围边界 - [通过/需改进/不适用]
...

### 10. 安全与破坏性 - [通过/需改进/不适用]
...

## 改进清单（优先级排序）

1. 🔴 必须修改：[...]
2. 🟡 建议修改：[...]
3. 🟢 可选优化：[...]

## 最终建议
[批准执行 / 修改后重新审核 / 需要补充信息]
```
